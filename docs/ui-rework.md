# 界面重构方案（面向最终用户）

分支 `ui/end-user-rework`。这份文档是这次重构的唯一依据：**先按它改，改完对着第 10 节的清单逐条验**。
文档里每一条判断都标了出处（规范来源见第 2 节），没出处的要么是现状事实，要么是要在本文档里定下来的约定。

---

## 1. 目标与判据

一句话：把五屏从「开发者的调试面板」改成「用户装上就敢用的通知拦截 App」。

现状的问题不是配色或圆角，而是**信息对象错了**：界面上大量文字、数字、按钮，说的是「模块端此刻读到什么」
「装配 OK 几 / SKIP 几」「扩展槽命中 9 · 漏斗判定 0」「生效配置 JSON」——这些是开发者排障时需要的，
最终用户既看不懂，也不需要。用户要的三件事只有：

1. **它在工作吗**（拦截开着没有、今天拦了多少）
2. **拦得对不对**（哪些被拦了、会不会误杀通话/闹钟/消息）
3. **我也能改**（哪些词要拦、哪个应用别动、抓得太紧还是太松）

判据（重构完成的定义）：

- 五屏首屏可见内容里，**不出现**任何一个只有读源码才知道含义的词（模块端、判定链、槽位、漏斗、装配、
  熔断、reason、delta、base、镜像、通道、JSON…）。
- 每屏进入后 1 屏内能看到该屏的主要操作或主要数据，不需要滚动越过说明文字。
- 每个开关旁不出现超过一行的副文本；页面上不再出现「三行以上连排的说明段」。
- 开发信息全部收进**设置 → 诊断**一屏，且诊断入口是明面可见的条目（不做连点 7 次）。

## 2. 规范依据

只列这次真正拿来判对错的条文（原文出处见链接）。

| 来源 | 采用的条文 |
|---|---|
| Android Settings 设计指南 <https://source.android.com/docs/core/settings/settings-guidelines> | ① 一屏一眼能看清全部设置项**及其当前值**；② 一屏最多 10–15 项，超了拆子屏；③ 标题简短具体，**副文本给当前状态/取值**而不是复述标题；④ 分组用分隔线聚类（不是给每一项都画线），有组标题就配分隔线；⑤ 主开关（main setting）置顶，关掉它时从属项置灰/隐藏，副文本一行说明被隐藏了什么；⑥ **渐进披露**：不常用项收进子屏，且只有 ≥3 项时才值得做；⑦ 单输入字段用对话框、多字段用全屏；⑧ 工具栏不做「长按才出来」的操作 |
| Material 设置 pattern <https://m1.material.io/patterns/settings.html> | ① 设置项 = 用户偏好；**应用自身信息（版本、许可）不属于设置页**，应去「关于/帮助」；② 标签简短、避免技术术语与 Set/Change/Manage 这类泛化动词；③ 副文本只在必要时出现；开关项的副文本写「打开后会发生什么」（一句话、动词开头、不加句号、不重复标签里的词），其他控件的副文本写**状态**；④ 项数 7±2，8–10 项用 1–2 个分组标题，11–15 项用 2–4 个标题 + Advanced 子屏 |
| Material 写作规范 <https://m2.material.io/design/communication/writing.html> | ① 简洁、可扫读，一段只讲一件事；② 用简单直白的词；③ 只讲完成当前任务**必需**的信息，不解释内部怎么实现（Chromium 同款条文：`Don't go behind the scenes` <https://www.chromium.org/user-experience/ui-strings/>）；④ 现在时；⑤ 单句不加句号、标签后不加冒号；⑥ 一句控制在 5–15 词；⑦ 不要为功能自造术语 |
| Material 3 排版与间距（本地 skill `material-3`） | 4dp 网格：组件内边距 4/8/12/16/24，组件之间 8/12/16/24，**区块之间 24/32/48**，页边距 16dp（compact）；卡片属 Containment，只给「自成一块」的内容，列表本身不该套卡片 |
| 本项目 AGENTS.md | 用户可见文案一律资源化（`values` 英文默认 + `values-zh-rCN`）、两包键逐条对应；ViewModel 只产出 `UiText`；**拨不动的控件旁边必须有一行说明原因与恢复方式**；文案改完跑 `check_string_format_args.py` |

关于「诊断」：Material 的条文把「应用信息」从设置页排除了，但本项目是 LSPosed 模块，排障入口对
**使用者本人**（装了 Xposed 的进阶用户）仍有价值，所以不做连点隐藏，而是**明确列在设置页最底部**，
标题就叫「诊断」，点进去是一屏开发信息——这也正好符合渐进披露（收进子屏，主屏只留一个入口条目）。

### 3.2 设置屏

- 顶部一张只有一行的卡片「框架服务：LSPosed 2.2.1」——应用/框架信息放设置页首屏，且占一整张卡。
- 「模块状态」卡里同时塞了：说明段、模块主行、计数行、装配行、熔断行、两个按钮、装配摘要、一个展开按钮、
  展开后的整段明细。**9 类信息挤在一张卡里**，且三行小字全是 `bodySmall` + 灰字，扫不出优先级。
- 熔断（safe mode）在界面上的表达是「模块端状态」，用户看不出「为什么会这样、我该做什么」。
- 「已生效配置」与「保护类型」读的是同一份数据源，界面上分成两个卡；配置 JSON 对用户没有意义。
- 计数器（扩展槽/漏斗/ROM/异常）是纯开发指标。
- 「观察模式」标签是开发者词汇，用户不知道「观察」是什么意思。

### 3.3 规则屏

- 「关键词规则」组：说明段（1 行）+ 开关 + 4 行高输入框 + 说明段（2 行）+ 48dp 按钮，控件被夹在说明之间。
- 输入框用 placeholder「每行一个关键词」当唯一提示，写起来后提示消失、不再知道格式。
- 「白名单」组：两段说明共 4 行（含「所以不必申请『读取已安装应用』权限」这种实现解释）。
- 「从模块端刷新候选」按钮文案带实现词；候选列表与「手动加包名」输入行分居两处，动作不连贯。

### 3.4 记录屏 / 学习屏 / 首页

- 记录屏：筛选用的是 `SegmentedButton`（好），但空状态、说明文案里带 reason 原文与「标注」「微调」等词。
- 学习屏：三栏标题分别是「待处理」「样本库」「拟合」，其中「拟合」「微调量」「base-only」是训练侧术语；
  归因说明是给开发者看的（CI 断言里那条 `attribution_base_only` 就是为了防止说明丢失）。
- 首页：统计与排行本身是用户要的，**保留现有设计**（用户明确说「首页还可以」）；只有顶部的
  `StatusCard` 文案（「框架服务：LSPosed 2.2.1」）需要改成用户语言。

## 4. 设计原则（本次落地版）

- **P1 只讲用户视角的事实**：写「通知会被拦下」，不写「判定链在第一步短路」。
- **P2 一屏一件事**：屏 = 数据（首页/记录）+ 需要用户决定的三件事（规则/学习）+ 偏好（设置）。
- **P3 状态进副文本，说明进 footer**：开关的副文本写状态或「打开后会发生什么」；整屏口径的说明放屏尾
  一行 `bodySmall`，不复述控件。
- **P4 渐进披露**：开发信息收进「诊断」子屏；一屏可见条目控制在 10–15 以内。
- **P5 一套零件、一套间距**：所有列表项走同一个零件；区块间距 24dp，屏边距 16dp（见第 7 节）。
- **P6 卡片只包「自成一块」的东西**：状态块、统计块用 `Card`；普通设置列表**不套卡片**，用组标题 + 分隔线。

## 5. 目标信息架构

### 5.1 设置（重写）

```
设置
├── [状态行] 已连接 / 未连接（未连接时给一行去处说明，见下）
├── 拦截垃圾通知              [开关]    ← 主开关，置顶
│     副文本：打开后，命中规则或判定为垃圾的通知不会弹出
├── 只看不拦（试用）          [开关]    ← 原「观察模式」，主开关关掉时置灰
│     副文本：照常判断并记录，但所有通知都会弹出
├── AI 识别                  [开关]
│     副文本：用端侧模型判断通知内容是不是垃圾，不联网
│     严格程度  宽松 [——●——] 严格
│     副文本：越严格拦得越多，也越可能误拦
├── 保护类型                 ← 组标题 + 分隔线
│   ├── 来电        [开关]
│   ├── 闹钟        [开关]
│   ├── 导航        [开关]
│   ├── 媒体播放    [开关]
│   ├── 前台服务    [开关]
│   └── 消息对话    [开关]
│     屏尾一行：这些通知永远不会被拦下
└── 诊断 →                   ← 列表项，进入诊断屏
```

- 删除：模块状态卡、装配明细、生效配置 JSON、LSPosed 版本、计数器、熔断面板（全部搬到诊断屏）。
- 删除每个开关下重复出现的「总开关关着：判定链整体短路…」长段；改为**从属项整行置灰 + 一行状态**
  「需先打开「拦截垃圾通知」」（AGENTS.md 的硬要求：置灰必须带原因与恢复方式）。
- 「六类保护」的副文本原本与标签同义（「闹钟/闹钟」「导航/导航」），全部删除，只留标签。
- 阈值滑块的数值（0.80）不再展示，改为两端标签「宽松 / 严格」，滑杆方向为「右 = 更严格 = 阈值更低」。

### 5.2 诊断（新屏，设置页底部入口）

保留现有全部开发信息，一屏看完，文案保持开发口径（这一屏的目标读者是排障的人）：

```
诊断
├── 框架服务行：LSPosed <版本> · 已连接 / 未连接
├── 模块状态：主行 + 计数行 + 装配行 + 熔断行
├── [刷新模块状态]  [清除熔断并恢复]（仅熔断时出现）
├── 「本次装配明细」展开区
├── 「生效配置 JSON」展开区
└── 版本：1.7.0+ci-release.0122e2a9（模块代码）
```

硬约束：CI 断言 `settings_refresh_status` / `settings_assembly_show` / `module_line_no_reply` /
`settings_clear_safe_mode` 四个键必须在包内且有中文值（<https://github.com/Vstory/NotifyGuard> 的
`build-ci.yml` ③j 段），所以这四个键**内容照搬**到诊断屏，不改名不删除。

### 5.3 规则（重写）

```
规则
├── 关键词                       ← 组标题
│     [输入框：label「关键词」，辅助文字「每行一个，命中即拦」]
│     [保存并生效]（Filled Button，唯一主操作）
├── 不拦截的应用
│     标题行右侧：[刷新候选]（图标按钮 + tooltip）
│     [搜索框：label「搜索」，辅助文字「应用名或包名」]
│     列表项：图标 + 应用名 + 包名 + [开关]
│     [手动填包名输入框] + [添加]
└── 屏尾一行：名单里的应用不参与内容判定；关键词规则仍然生效
```

- 删除：「候选取自模块端记录里出现过的包名 —— 有记录就是发过通知的那些。所以不必申请…权限」（实现解释）。
- 删除：「打到一半就下发会被按半截词拦通知，所以只由下面的按钮提交」——改为按钮副文本「保存后立即生效」。
- 「记录里出现过 N 次」保留（对用户有用：帮他判断这应用值不值得放行），位置沿用上一版的 supporting 内第二行。

### 5.4 记录（改造）

- 保持 `SegmentedButton` 筛选与列表结构；条目三行内说完：应用名 / 通知标题 / 时间 + 结果徽标。
- 结果词统一为：**已拦截 / 本该拦截 / 已放行**；原因走现成的 `ReasonInfo` 人话，原文 reason 只在诊断屏出现。
- 空状态给一句「还没记录到通知 + 可能的原因（模块未连上 / 刚装上）」。
- 标注动作（标为垃圾 / 标为正常 / 撤销）保留，文案去掉「微调」「样本」等训练侧词。

### 5.5 学习（改造）

- 三栏改名：`待确认` / `已标注` / `学习结果`（原「待处理」「样本库」「拟合」）。
- 「拟合」栏里删掉技术串（base-only、delta 摘要、指纹），改成：上次学习时间、学到的样本数、
  「重新学习」按钮 + 门槛未达时的一行说明（保持 `learning_sample_delete` / `learning_sample_to_ham` /
  `attribution_base_only` 三个被 CI 断言的键仍在包内）。
- 归因说明改成用户语言：「这条是按出厂模型判的」/「这条受你的标注影响」。

### 5.6 首页（保持 + 文案）

- 结构不动。仅把 `StatusCard` 的文案从「框架服务：LSPosed 2.2.1」改成用户语言：
  「已连接」/「未连接，点右上角刷新」；LSPosed 版本号移到诊断屏。

## 6. 文案规范

### 6.1 禁用词表（出现在用户可见文案里即为不合格）

| 禁用 | 改用 |
|---|---|
| 模块端 / 模块侧 | （省略，或「后台服务」） |
| 判定链 / 短路 / 放行 | 不拦截 / 直接弹出 |
| 命中规则 / 规则命中 | 符合你的关键词 |
| reason / 原因字段 | 原因 |
| 扩展槽 / 漏斗 / 装配 / SKIP / FAIL | （不出现，诊断屏除外） |
| 熔断 / safe mode | （诊断屏用「已进入安全模式」） |
| 阈值 / 分数 / 0.80 | 严格程度 |
| 微调 / delta / base / 样本库 / 拟合 | 学习 / 标注 |
| 镜像 / 通道 / 广播 / 远程文件 | （不出现） |
| JSON / 配置镜像 / 生效值 | （诊断屏除外） |
| 观察模式 | 只看不拦（试用） |

### 6.2 句式

- 一句 ≤ 20 字（中文）/ ≤ 12 词（英文），一段只讲一件事。
- 单句结尾不加句号；多句才加。
- 标签不加冒号、不以「设置/管理/修改」开头。
- 开关副文本：动词开头，写「打开后会怎样」（如「命中关键词的通知不会弹出」）。
- 整个区块的口径说明放**屏尾**一行 `bodySmall`，不复述上面的控件。
- 不出现 `**粗体**` 标记以外的富文本；`Note()` 的加粗只用于真正的重点词，且每屏 ≤ 2 处。

### 6.3 两种语言的对应

- 英文用 sentence case，动词开头；中文用直陈句。两包键逐条对应（CI 会查）。
- 占位符个数与类型必须一致，改完跑 `scripts/check_string_format_args.py --strict --call UiText.Res .`。

## 7. 组件与间距规范

间距常量（新增到 `ScreenParts.kt`，替代散落的 `8.dp`/`16.dp` 字面量）：

| 名称 | 值 | 用途 |
|---|---|---|
| `ScreenPadding` | 16.dp | 屏幕水平内边距 |
| `SectionGap` | 24.dp | 区块之间 |
| `ItemGap` | 8.dp | 区块标题与其首条内容之间 |

组件约定：

| 场景 | 组件 | 说明 |
|---|---|---|
| 开关项 | `ListItem` 整行 `toggleable`（现有 `SwitchRow`） | 副文本 ≤ 1 行；标签 `bodyLarge`、副文本 `bodyMedium` |
| 可点条目（进子屏 / 展开） | `ListItem` + trailing 图标 | 不用 `OutlinedButton` 当展开按钮；尾图标 `KeyboardArrowDown/Up` 或 `ChevronRight` |
| 主操作（保存、添加） | Filled `Button`，`heightIn(min = 48.dp)` | 一屏最多一个 |
| 次操作（刷新） | `OutlinedButton` 或标题行尾 `IconButton` | |
| 单字段输入 | `OutlinedTextField` + `label` + `supportingText` | 不再用 placeholder 当格式说明 |
| 多行输入 | `OutlinedTextField` + `label`，`minLines = 3` | |
| 滑块 | `Slider` + 两端 `labelSmall` 标签 + 一行副文本 | 不显示原始数值 |
| 状态/统计块 | `Card`（现状保留） | 只用于首页统计与诊断状态 |
| 分组 | 组标题 `titleSmall` + 组首/组尾 `HorizontalDivider` | 不再给每个分组套卡片 |

无障碍：整行可点、`Switch` 的 `onCheckedChange = null`、读屏把整行当一个带名字的开关（沿用现状）；
触摸目标 ≥ 48dp；置灰项必须带原因文案。

## 8. 诊断入口

- 位置：设置屏最后一个条目，`ListItem`（无卡片），标签「诊断」，trailing 右箭头。
- 进入后是独立 `Scaffold` 屏（`ui/screen/DiagnosticScreen.kt`），顶栏有返回。
- 不加连点门槛 —— 用户明确要求「直接提供一个诊断入口，不要点 7 次」。
- 内部文案保持开发口径（这一屏的读者是排障者），但**新增一行屏尾说明**：
  「这一屏是排障用的技术状态，日常使用不需要看」。

导航落点：`ui/Destination.kt` 加 `Diagnostic`；`MainActivity` 的 `NavHost` 加路由。

## 9. 实施步骤

每一步一个提交，**本地先跑三件套**再推：

```bash
python3 scripts/check_string_format_args.py --strict --call UiText.Res .
python3 scripts/check_log_events.py .
./gradlew --offline :app:compileDebugKotlin
./gradlew --offline :app:testDebugUnitTest
```

| 步 | 内容 | 提交信息 |
|---|---|---|
| 0 | 本方案文档 | `docs(ui): plan the end-user UI rework` |
| 1 | `ScreenParts` 扩零件（间距常量、可点条目、说明行）+ 设置屏重写 + 诊断屏新建 + 路由 | `refactor(ui): rebuild settings for end users and move dev info to diagnostics` |
| 2 | 规则屏重写（关键词 / 白名单两组，去实现解释） | `refactor(rules): rebuild the rules screen around user tasks` |
| 3 | 记录屏文案与条目排版 | `refactor(records): speak user language in the record list` |
| 4 | 学习屏改名与归因文案 | `refactor(learning): rename the tabs and drop training jargon` |
| 5 | 首页状态行文案 + 五屏间距统一 | `refactor(ui): align the home status line and unify screen spacing` |

依赖顺序：1 建立零件，2–5 复用；每步都必须能独立编译、独立可用（不做半截状态）。

## 12. 风险

| 风险 | 处置 |
|---|---|
| 改文案导致 CI 的资源断言失败 | 被断言的键改名/搬屏时保持键名不变；推前本地跑文案脚本，推后看 CI 的产物断言档 |
| 移除设置屏的「模块状态」后，非技术用户遇到「装了没生效」无从下手 | 诊断屏保留；未连接时首页与设置屏都给一行「去诊断看看」的指引 |
| Compose 代码无法本地跑 UI 测试 | 逻辑继续抽在 ViewModel 纯函数里（现有口径）；UI 改动由用户真机验收 |
| 一次改四屏、真机验收困难 | 按第 9 节分 5 个提交，逐屏可单独验收 |
